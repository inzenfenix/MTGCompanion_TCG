**Key constraints this plan is designed around** (from surveying the actual
backend code, not assumed):
- `storage.service.ts` already targets plain `@aws-sdk/client-s3` and is
  deliberately endpoint-agnostic — leaving `STORAGE_ENDPOINT`/
  `STORAGE_FORCE_PATH_STYLE` unset (today only set for local MinIO) makes it
  hit real S3 with **zero code changes**. Photos move via presigned PUT/GET
  URLs the client calls directly — the bucket needs real CORS config, since
  MinIO's dev CORS setup (`minio-init` in docker-compose) doesn't carry over.
- `notifications/` already has a real `SesEmailProvider` seam
  (`EMAIL_PROVIDER=ses`) alongside the MailHog-targeting SMTP one — but if
  the AWS account behind this is an Academy/Vocareum-style lab account, SES
  send access is commonly blocked/sandboxed; plan for `EMAIL_PROVIDER=smtp`
  against some external relay as the realistic fallback, not a hard blocker.
- **No Dockerfile for the backend exists yet** — writing one (multi-stage
  Node build, `npm run build` → `node dist/main`) is a prerequisite piece of
  work this plan depends on, not something Terraform itself produces.
- `VITE_API_BASE_URL` is a **Vite build-time env var**, statically inlined
  into the JS bundle — there is no runtime config mechanism. Pointing the
  APK at the new server means: get Terraform's output URL → set it in
  `trading-app-ionic/.env` → `npm run build` → `npx cap sync android` →
  `gradlew assembleDebug` again. Same for `PUBLIC_API_URL` (the backend's
  own env var, needed for MercadoPago's webhook to call back).
- Android blocks plaintext HTTP by default (API 28+) unless explicitly
  allowlisted — so either the server needs real TLS (a domain + Let's
  Encrypt/ACM, which needs its own plan if no domain is available yet), or
  `android/app/src/main/res/xml/network_security_config.xml` needs an
  explicit cleartext exception for the server's host, which is fine for
  course-project testing but should be called out as *not* a production
  answer.
- The credential-rotation requirement below (easy-to-swap access/secret/
  session key) is the strongest signal this targets an AWS Academy Learner
  Lab-style account — those hand out **temporary** credentials (access key +
  secret key + session token) that expire every few hours, unlike a normal
  IAM user's long-lived keys. The plan below assumes that shape but doesn't
  require it.
