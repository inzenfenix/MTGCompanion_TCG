**Key constraints this plan is designed around** (from surveying the actual
backend code, not assumed):
- `storage.service.ts` already targets plain `@aws-sdk/client-s3` and is
  deliberately endpoint-agnostic — leaving `STORAGE_ENDPOINT`/
  `STORAGE_FORCE_PATH_STYLE` unset (today only set for local MinIO) makes it
  hit real S3 with **zero code changes**. Photos move via presigned PUT/GET
  URLs the client calls directly — the bucket needs real CORS config, since
  MinIO's dev CORS setup (`minio-init` in docker-compose) doesn't carry over.
- `notifications/` already has a real `SesEmailProvider` seam
  (`EMAIL_PROVIDER=ses`) alongside the MailHog-targeting SMTP one — but if
  the AWS account behind this is an Academy/Vocareum-style lab account, SES
  send access is commonly blocked/sandboxed; plan for `EMAIL_PROVIDER=smtp`
  against some external relay as the realistic fallback, not a hard blocker.
- **No Dockerfile for the backend exists yet** — writing one (multi-stage
  Node build, `npm run build` → `node dist/main`) is a prerequisite piece of
  work this plan depends on, not something Terraform itself produces.
- `VITE_API_BASE_URL` is a **Vite build-time env var**, statically inlined
  into the JS bundle — there is no runtime config mechanism. Pointing the
  APK at the new server means: get Terraform's output URL → set it in
  `trading-app-ionic/.env` → `npm run build` → `npx cap sync android` →
  `gradlew assembleDebug` again. Same for `PUBLIC_API_URL` (the backend's
  own env var, needed for MercadoPago's webhook to call back).
- Android blocks plaintext HTTP by default (API 28+) unless explicitly
  allowlisted — so either the server needs real TLS (a domain + Let's
  Encrypt/ACM, which needs its own plan if no domain is available yet), or
  `android/app/src/main/res/xml/network_security_config.xml` needs an
  explicit cleartext exception for the server's host, which is fine for
  course-project testing but should be called out as *not* a production
  answer.
- The credential-rotation requirement below (easy-to-swap access/secret/
  session key) is the strongest signal this targets an AWS Academy Learner
  Lab-style account — those hand out **temporary** credentials (access key +
  secret key + session token) that expire every few hours, unlike a normal
  IAM user's long-lived keys. The plan below assumes that shape but doesn't
  require it.

**Design decisions — resolved (17 ago), user's own answers, recorded so
nobody re-litigates them:**

- **Price editing → buyer counter-offers, not a static listing.** The
  seller's listed price is a starting ask, not a fixed price — buyers can
  propose their own amount.
- **Race/locking → this is the SAME mechanic as price editing, not a
  separate rule.** User's own words: "let's do it auction style, both of
  them gets connected and give their price, after 5 seconds the last
  offer gets the card." Restated precisely: a listing accepts live offers
  from any interested buyer; every connected participant (seller + all
  active bidders) sees the current highest/most-recent offer in real
  time; each new offer resets a 5-second countdown; once 5 seconds pass
  with no new offer, the listing locks to whoever made that last offer,
  at their offered amount. This answers BOTH original questions at once —
  there's no separate "first PAID wins" fallback to build, the auction
  itself IS the concurrency-resolution mechanism. **This is a materially
  bigger feature than either original question implied on its own** — see
  the new J12/J13/J14 rows below, and the implementation notes under each:
  - Needs real-time connectivity (buyers + seller seeing each other's
    live offers) — confirmed via `grep` that this backend has **no**
    WebSocket infrastructure today (no `@nestjs/websockets`/`socket.io`
    dependency, no `WebSocketGateway` anywhere in `backend/src/`) — this
    is a new capability, not wiring onto something that exists.
  - Needs a new `Offer`/`Bid` schema (cardId or listingId, bidderId,
    amount, createdAt) — the transaction's final agreed price becomes
    whichever offer wins the auction, not `Card.guessedPrice` — J6/J8's
    payment/receipt flow now triggers off the auction's resolved winner,
    not off a flat "buyer taps Buy at the listed price."
  - The countdown must be enforced **server-side**, not trusted from the
    client — a client-side-only timer would be trivially game-able (a
    bidder's own app just "forgets" to report a competing offer arrived).
    Concretely: each new offer stamps a `closesAt = now + 5s` column;
    resolving the winner reads "no offer newer than `closesAt - 5s` AND
    `now > closesAt`," not a countdown UI has to be trusted for.
  - Open question NOT re-asked this session (implementer's call, small):
    does a lone bidder with zero competition still wait the full 5
    seconds before winning, or does matching/exceeding the seller's own
    ask close it instantly? The user's description describes the
    multi-bidder case; a single-bidder fast path is a reasonable,
    backward-compatible addition, not a contradiction of the mechanic —
    flag it, don't silently assume either way.
- **Listing persistence → real DB row, `Card.origin` flag.** Confirms
  J1's own recommended default — no change needed to that row.
- **Efectivo timeout → auto-expire.** A pending cash transaction with no
  seller confirmation auto-cancels after a timeout window (exact duration
  not specified by the user — implementer's call, e.g. 24h, should be a
  named constant not a magic number buried in code).
- **QR payload security → sign it now, as part of J4, not deferred.**
  The QR payload gains a short-lived signed token instead of shipping a
  bare `TRADE:<cardId>` — do this in the SAME change that adds real QR
  scanning (J4), not as separate later work.
- **Unchanged from the original writeup, still true, not re-asked:** the
  "invoice" is an informal receipt, not a real SII-authorized tax
  document — F2's existing disclaimer already establishes this, and J8's
  emailed version must carry the same disclaimer in the email body
  itself, not just the app UI.
